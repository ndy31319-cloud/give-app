# 나눔 요청과 채팅 예약

## 실행

1. 루트에서 `npm run migrate:trades` 실행 후 백엔드를 재시작한다.
2. 앱의 나눔글 상세에서 **나눔 요청하기**를 누른다.
3. 작성자는 생성된 채팅방의 요청 카드에서 **수락 / 거절**을 선택한다.
4. 수락 후 기존 카카오맵 약속장소 공유로 일정을 협의한다.
5. 전달 후 작성자가 **나눔 완료**를 누른다. 신청자 또는 작성자는 진행 중인 거래를 취소할 수 있다.

## 상태

- 신청 즉시 게시글 `reserved`, 신청 `pending`. 물품당 진행 중인 요청은 한 개다.
- 수락 시 신청 `approved`, 게시글은 `reserved` 유지.
- 거절/취소/대기 24시간 만료 시 게시글 `open`으로 복귀.
- 완료 시 신청과 게시글 모두 `completed`.
- 수락된 요청은 24시간 만료 대상이 아니다.
- 서버는 30초마다 만료 및 채팅 재전송을 처리하며, 요청 생성/조회/처리에서도 만료 여부를 확인한다.
- 기존 신청은 만료시간과 채팅방을 자동 부여하지 않는다. 기존 비대면 수령 API는 유지한다.

## API

모두 JWT 인증 필요. 클라이언트가 전달한 회원 번호는 사용하지 않는다.

- `POST /api/trades/posts/:donateId`: 요청 생성. 같은 사용자의 활성 요청 재시도는 같은 요청/채팅방을 반환한다.
- `GET /api/trades/:id`: 당사자만 조회.
- `POST /api/trades/:id/approve`, `/reject`: 작성자만 처리.
- `POST /api/trades/:id/cancel`: 양쪽 당사자 처리 가능.
- `POST /api/trades/:id/complete`: 작성자만 승인된 거래 완료 가능.

## 저장과 복구

MySQL의 `PICKUP_REQUEST`가 거래 상태의 기준이다. 기존 테이블에 채팅방 ID, 만료/종료 시각, 채팅 동기화 여부를 추가한다. 기존 상태 `picked_up`도 유지한다.

게시글 잠금과 트랜잭션으로 동시 요청·상태 충돌을 막는다. Firestore의 `chatRooms/trade_<pickup_id>`와 `messages/request_<pickup_id>`는 고정 ID를 사용한다. DB 커밋 후 Firestore 전송이 실패하면 `chat_synced = FALSE`가 남아 재시작 후에도 재전송할 수 있다. 이 경우 신규 생성 API는 재시도를 안내하지만 이미 저장된 요청은 중복 생성하지 않는다.

진행 중에는 게시글 직접 상태 변경·삭제·채팅방 나가기를 제한한다. 요청 카드의 버튼은 서버에서 현재 상태와 당사자 권한을 다시 확인한다. 과거 종료 카드가 다른 진행 중인 거래의 게시글 상태를 바꾸지 않도록 현재 게시글 상태도 응답한다.

## 검증

- `npm test`: 권한 및 허용 상태 전이 테스트. 외부 서비스 사용 없음.
- `npm run test:trades:integration`: 설정된 MySQL/Firestore에 전용 임시 회원·게시글·채팅방을 만들고 종료 시 해당 ID만 삭제한다. 실제 서비스 데이터는 테스트 대상으로 사용하지 않는다.
- `frontend-app`에서 `npx tsc --noEmit`: 앱 타입 검사.

기부함 연동 및 실시간 위치 추적은 이 변경에 포함하지 않는다. 푸시 발송은 없으며 기존 알림 조회와 채팅 목록 새로고침으로 요청을 확인한다.
